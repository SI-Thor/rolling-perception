**What kills trust in week 2 / month 2 that day-1 precision misses**

1. **Precision is measured on the wrong denominator.** Day-1 precision = true events / fired events on a *seeded* set of streams the user cared about during setup. By week 2 the household adds streams (a new camera, a podcast feed, a text feed) that were never in the calibration set. The 0.9 threshold is a *per-source* number, but the failure mode is *per-source-class and per-time-of-day*: a porch camera is 0.98 at noon and 0.4 at 2am (headlights, rain, IR bloom). The aggregate stays above 0.9; the user's 2am phone buzz is the one they remember. **Measure precision stratified by (source × hour × weather/lighting regime), not per stream.** Auto-demote on the *worst stratum* with a minimum sample, not the mean.

2. **The 1-false-per-stream-per-day target is unfalsifiable at household scale.** A stream that fires 0.3 events/day can't distinguish 1/day from 0.1/day without weeks of data. The spec's own correction loop (one-tap) gives you maybe 2–5 labels/week/stream. You will be *below the statistical resolution* of your own trust contract for months. **Measure time-to-N-labels and report confidence intervals on precision, not point estimates.** A stream at "0.92 ± 0.15 (n=11)" is not passing; it's unknown. The system should treat unknown as feed-only until n is sufficient — which means the default should be *quieter* than the spec implies, and the spec should say so.

3. **False *negatives* are invisible and corrosive.** The trust spec only counts false events. But the "what changed" feed's real promise is silence-means-nothing-happened. A missed event (the package, the kid, the leak) doesn't generate a correction tap — the user doesn't know to tap. Month 2 is when the user *notices* the feed missed something they saw on the camera. That single miss destroys more trust than ten false alarms, because it retroactively invalidates every silence. **Measure recall on a sampled audit**: periodically re-run reflective perception on a random window and diff against what the feed reported. Report "audited recall" alongside precision. You cannot get this from user taps.

4. **The diff-gate drift is a slow trust leak, not a fast one.** The honest caveat — skipped tiles drift 0.20 vs 0.48 — means the gate is systematically *undersampling* gradual change. Gradual scenes (dusk, a slowly filling driveway, a plant growing, a person loitering) are exactly the ones the gate skips 88% of the time. Day-1 precision looks great because gradual changes rarely fire. Month 2 is when the user realizes the feed never told them about the thing that happened slowly. **Measure recall specifically on gradual-change ground truth, and track the drift gap over time as a leading indicator.** If skipped-tile drift rises, precision is about to fall.

5. **Auto-demotion is a cliff with no explanation.** A stream crossing 0.9 → feed-only is a *silent* behavior change. The user set "spend freely on the front door," and one week later the front door stops pushing. They will read this as the box being broken, not as the box being honest. **Demotion must be a visible, explained event with a one-tap "I disagree, re-promote" and a shown reason ("3 of your last 4 corrections said these were false").** Otherwise the trust model's own safety mechanism becomes the trust-destroying event.

6. **The reflective judge is advisor-only for a reason — but its 0.47s calls are in the loop for *explanations*.** If the "why did this fire" text is generated by the same model that was demoted from tie-breaking, month 2 is when users notice the explanations are confidently wrong ("person at door" when it was a raccoon). Wrong explanations train users to distrust *correct* alerts. **Explanations must be grounded in the reflex/decision evidence (which tiles, what embedding distance, what the ledger's normal was), not in reflective prose.**

7. **Cross-stream correlation is the unmeasured trust bomb.** The feed is "cross-stream," but the trust spec is per-stream. The first time two streams fire on the same real event (doorbell + porch cam), the user sees two events for one thing — or worse, the system *merges* them and misses that they were different. **Measure duplicate-event rate and merge-error rate across streams.** Neither is in the spec.

**What to measure instead**

- Precision and **audited recall** stratified by source × hour × lighting/weather regime, with n and confidence intervals shown.
- **Time-to-label** per stream; treat low-n as unknown → feed-only.
- **Skipped-tile drift gap** over time (leading indicator of gradual-change recall loss).
- **Duplicate/merge error rate** across correlated streams.
- **Demotion/re-promotion churn** — a stream oscillating across 0.9 is a signal the threshold is wrong for that source, not that the source is bad.
- **User correction latency and rate** — if corrections drop to zero, either it's perfect or the user gave up. Distinguish these.

**What the system should do when it starts being wrong in a new way**

- **Detect regime shift, not just low precision.** A stream whose *correction rate* jumps, or whose embedding-distance distribution shifts (new normal appearance), or whose rhythm/jitter changes (camera moved, lighting changed) should trigger a *recalibration* state — feed-only, visible banner, "this camera's normal changed; relearning" — before precision has time to fall below 0.9. Precision lags the cause by weeks; distribution shift leads it.
- **Widen uncertainty, don't just demote.** New-way-wrong means the model's confidence is miscalibrated. The response is to *raise the bar for firing* (require corroboration across two perception speeds, or two streams) and *lower the bar for explaining*, not to silently drop to feed-only.
- **Surface the miss, not just the false alarm.** When the audit finds a missed event, tell the user: "I didn't flag this; here's why." That converts an invisible trust loss into a visible, correctable one.
- **Never let the trust contract be a number the system can't measure.** If n is insufficient, the honest state is "unknown," and unknown must be quieter than the spec's 1/day — because the spec's number is a promise the data can't yet back.
