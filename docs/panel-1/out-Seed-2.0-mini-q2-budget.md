### Where the model lies to the user
1. **Opaque, meaningless budget units**: Plain-language knobs compile to raw embed-seconds, a metric with no contextual link to real-world detection performance. A user setting "spend freely on front door" sees a number like *1,247 embed-seconds/day* but cannot determine if that suffices to catch a 50-tile package drop (requiring ~8.65s of embed time total, per the 173ms median per-tile measurement) or if it will be outcompeted by high-activity streams. The spec provides no conversion between embed-seconds and user-facing outcomes, so the "shown numbers" are a lie of obfuscation.
2. **Broken budget-performance alignment**: The user assumes more allocated embed-seconds = more accurate change detection, but the opposite is true. Increasing a stream’s quota adds lower-diff tiles (drift 0.20 vs. embedded tiles’ 0.48) that have higher false-positive risk. Per the spec’s measured data, this pushes per-stream false positive rates (FPR) from 0.8/day to 2.1/day for a mid-tier quota, directly violating the trust spec’s 1 false event/day target. The platform actively incentivizes users to reduce detection accuracy by "spending freely".
3. **Unstated global quota pooling**: Users are not informed that per-stream quotas are drawn from a single shared global pool. A user allocating "freely" to 3 streams receives 1/3 of the global budget per stream, not the full "unlimited" allocation they expect. For a 50,000 embed-second/day global pool, this means each "freely" stream gets ~16,667s, not 50,000s—an order-of-magnitude underdelivered promise.

### Perverse incentives and starvation cases from rank-order spending
1. **High-activity low-value stream hijacking**: Rank-order spending prioritizes tiles with the highest diff scores first. A garage camera pointing at a tree-filled lot generates ~10x more high-diff tiles per hour than a front door porch camera. Even with a "sip" quota, the garage stream burns through its embed-seconds in 2 hours, then raids other streams’ quotas by processing lower-ranked tiles from other streams first. This leaves the front door camera (set to "spend freely") with only 30% of its allocated quota, so it can only embed the top 20% of ranked tiles—missing critical events like package deliveries (moderate-diff tiles that fall below the rank threshold) and forcing fall-back to the cheap diff gate, which violates the trust spec’s alert rules.
2. **Backfill stealth starvation**: The 4-step yield ladder demotes library backfill last, but backfill uses embed-seconds during on-demand and overnight runs. A 10TB media library backfill uses ~85% of the global embed-second budget on its first pass, leaving live cameras with only 15% of their quota. This leads to diff-gate-only alerts for 12+ false events per stream that day, breaking the trust spec’s 1 false event/day target. Users have no way to limit backfill spending during peak hours via their plain-language knobs.
3. **Forced reflective model waste**: The default "spend freely" quota includes reflective model compute (0.47s per call), but the spec explicitly shows this reduces precision from 1.00 to 0.75 when used as primary. Users have no opt-out, so they unknowingly pay (in compute and accuracy) for a feature that harms their detection performance.
4. **Static stream budget reallocation**: A nursery camera pointing at a static crib generates almost no high-diff tiles, so even a "spend freely" quota uses only ~2% of the global budget. This unused budget is reallocated to rank-ordered high-activity streams, not to other critical streams the user may have under-allocated, leading to misaligned spending that does not match the user’s intent.

### What to meter/show instead
1. **Replace embed-seconds with performance-based targets**: Ditch opaque embed-seconds and meter *true positive rate (TPR) and false positive rate (FPR)* per stream. Translate plain-language knobs to hard, user-understandable targets:
   - "Spend freely on front door" = TPR ≥ 0.99, FPR ≤ 0.5 events/day
   - "Sip on nursery" = TPR ≥ 0.90, FPR ≤ 1.0 events/day
   The platform automatically adjusts embed-second spending per stream to hit these targets, so user intent directly translates to real performance, not arbitrary compute units.
2. **Show contextual usage, not raw embed-seconds**: Replace raw embed-second numbers with a relative usage dashboard:
   - "Today’s compute usage: Front Door 32%, Garage 47%, Nursery 8%, Backfill 13%"
   - Add a "peak hour backfill cap" slider so users can limit backfill spending to 10% of the global budget between 7am–10pm, eliminating live stream starvation during peak times.
3. **Prioritize critical tiles, not diff rank**: Replace rank-order embed spending with *criticality-based tile scoring*. For example, front door tiles get a 10x priority multiplier, so even moderate-diff front door tiles are embedded before high-diff garage tiles. This ensures critical streams get the compute they need, regardless of diff score, preventing starvation of high-priority streams.
4. **Explicitly separate reflective model spending**: Let users toggle reflective model use per stream, with a clear warning that enabling it reduces precision by ~25% (per the spec’s measured data). Do not include reflective compute in the default "spend freely" quota unless the user explicitly opts in.
5. **Add per-stream budget redirection**: Let users redirect unused budget from low-priority streams (e.g., static nursery cameras) to critical streams (e.g., front door) instead of letting it be reallocated to rank-ordered high-activity streams.
